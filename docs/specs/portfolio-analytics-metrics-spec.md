# Portfolio Analytics Metrics Spec

## 1. Purpose
Контракт для продуктовой аналитики портфолио-сайта.

Документ фиксирует:
- какие события считаются source of truth;
- какие ключевые сценарии анализируются;
- какие метрики считаются поверх событий;
- как интерпретировать значения;
- какие правила должен соблюдать дальнейший ручной анализ данных.

Цель аналитики:
- измерять не "контакт" как главный KPI;
- измерять интерес к кейсам;
- измерять использование ключевого функционала;
- отделять случайный просмотр от осмысленного взаимодействия.

## 2. Scope
Спека относится к:
- сайту `rodyukov.art`;
- счетчику `Yandex Metrica`;
- событиям, отправляемым из текущего Next.js-проекта;
- ручному weekly-анализу данных из интерфейса и экспортов Метрики.

Спека не описывает:
- маркетинговую атрибуцию;
- performance-мониторинг;
- Webvisor, replay, heatmaps;
- CRM, офлайн-конверсии и hiring funnel вне сайта.

## 3. Product Analytics Goal
Главная аналитическая цель:

`оценивать качество вовлечения в кейсы и полезность ключевого функционала внутри кейсов`

Главный объект анализа:
- не прямой переход в контакт;
- не pageviews сами по себе;
- а признаки профессионального интереса к работам и сценариям их просмотра.

## 4. Primary Questions
Аналитика должна отвечать на следующие вопросы:

1. Открывают ли пользователи кейсы после входа на главную.
2. Исследуют ли пользователи несколько кейсов, а не один случайный.
3. Прокручивают ли полные кейсы глубоко и смотрят ли их продолжительное время.
4. Используют ли пользователи `short mode`.
5. Помогает ли `short mode` перейти к следующему осмысленному действию.
6. Используют ли пользователи fullscreen media.
7. Замечают ли пользователи интерактивную механику главной.
8. Переходят ли пользователи на страницу `About`.

## 5. Source Events
Ниже перечислены source events, которые считаются каноническими для аналитики.

### 5.1 Home Events
- `view_home`
  - просмотр главной страницы.
- `home_preview_open`
  - первое открытие hover-preview в рамках клиентского состояния главной страницы.
- `home_preview_change`
  - переключение preview с одного кейса на другой на главной.
- `click_case_card`
  - переход в кейс с главной страницы.

### 5.2 Case Events
- `view_case`
  - открытие страницы кейса.
- `view_second_case`
  - открытие второго уникального кейса в рамках измерительной сессии вкладки, однократно.
- `case_scroll_90`
  - достижение глубины 90% на странице кейса в полном режиме.
- `case_read_120s`
  - суммарные 120 секунд просмотра полных кейсов в видимой вкладке за измерительную сессию.

### 5.3 Feature Events
- `short_mode_toggle_on`
  - включение сокращенного режима кейса.
- `short_mode_toggle_off`
  - возврат из сокращенного режима в полный кейс.
- `image_fullscreen_open`
  - открытие медиа в fullscreen.

### 5.4 Static Page Events
- `view_about`
  - открытие страницы `About`.

## 6. Event Semantics

### 6.0 Границы измерения и контракт данных

Основная единица продуктового отчета — визит Метрики. Локальное накопление времени и дедупликация событий используют измерительную сессию одной вкладки в `sessionStorage`. Это разные сущности:
- локальное состояние сохраняется при переходах и перезагрузке страницы;
- после 30 минут без учитываемой локальной активности состояние сбрасывается; локальная активность — вход в кейс, глубокий скролл или засчитанный фрагмент просмотра полной версии в видимой вкладке;
- вкладки не объединяются, а браузер может скопировать начальное `sessionStorage` при дублировании вкладки;
- при недоступном хранилище используется память страницы, без гарантии сохранения при reload;
- собственные `user_id` и `session_id` не создаются и не отправляются;
- визит Метрики определяется ее счетчиком, его таймаутом и правилами атрибуции, поэтому совпадение границ не гарантируется.

`view_second_case` — практический сигнал изучения нескольких кейсов в одной вкладке, а не точный счетчик уникальных работ во всех вкладках визита. Его нельзя использовать для расчета среднего числа кейсов. Точное число уникальных кейсов за визит считается из `view_case` с группировкой по визиту Метрики и дедупликацией по `case_slug`.

Источник допустимых имен и обязательных параметров — типизированный контракт в `lib/analytics/`. Общий контекст — `page_path`; события кейсов дополнительно содержат `case_slug`, `case_title`, а `view_second_case` — `case_slug` и `previous_case_slug`. Short Mode сохраняет только `page_path`. Полноэкранное событие содержит `image_index` (с 1), `media_kind`, `gallery_variant`. В payload не добавляются собственные идентификаторы пользователей.

Просмотры страниц (`hit`) отправляются при первом входе и SPA-переходах. Параметр `route_change` равен `false` при первом входе и `true` при переходе. Повторный запуск эффекта для того же адреса не создает дополнительный `hit`.

### 6.1 `view_home`
Считается как page-level event.
Может срабатывать несколько раз у одного пользователя:
- при повторных заходах;
- при reload;
- при повторных визитах.

### 6.2 `home_preview_open`
Срабатывает только на первое открытие preview на главной в рамках одного клиентского состояния страницы.

Смысл:
- сигнал, что пользователь вообще заметил и активировал механику preview.

### 6.3 `home_preview_change`
Срабатывает при переходе между разными preview на главной.

Смысл:
- сигнал, что пользователь не просто задел hover, а начал исследовать список кейсов через механику главной.

### 6.4 `click_case_card`
Срабатывает при переходе в кейс с главной.

Смысл:
- главный action-bridge между главной и кейсами.

### 6.5 `view_case`
Срабатывает на открытие страницы кейса.

Смысл:
- базовый event входа в содержательный контент.

### 6.6 `view_second_case`
Срабатывает один раз при открытии второго уникального slug в измерительной сессии вкладки. Повторный просмотр первой работы, третья работа и возвраты назад не создают дополнительных срабатываний. После истечения локальной сессии набор уникальных кейсов начинается заново.

Смысл:
- сильный сигнал интереса выше, чем одиночный `view_case`.

### 6.7 `case_scroll_90`
Срабатывает только для полной версии, один раз на кейс за измерительную сессию. Порог — 90% доступной прокрутки страницы, а не доказательство прочтения 90% текста. Краткая версия не участвует; смена кейса не переносит флаг предыдущей работы. В отчетах важна доля визитов, где порог достигнут хотя бы в одном кейсе.

Смысл:
- сигнал глубокого просмотра страницы; сам по себе не доказывает чтение или понимание.

### 6.8 `case_read_120s`
Русское название: «Продолжительный просмотр кейсов — 120 секунд».

Срабатывает один раз при накоплении 120 секунд в полной версии одного или нескольких кейсов за измерительную сессию вкладки. Например, 70 секунд в одном кейсе и 50 секунд в другом дают одно достижение. Скрытая вкладка, краткий режим, главная и About не увеличивают время. Паузы не обнуляют накопленное время до окончания сессии. Смена кейса и reload сохраняют прогресс, если доступен `sessionStorage`.

Используется измеренное прошедшее время; разрыв между измерениями больше 5 секунд целиком отбрасывается как возможный сон устройства или задержка браузера. Это консервативная оценка: задержка таймера может привести к недоучету, но не должна мгновенно засчитать несколько минут. При скрытии вкладки, переключении режима и уходе со страницы сохраняется последний допустимый фрагмент. `case_slug` и `case_title` указывают работу, на которой достигнут порог, но не означают, что все 120 секунд проведены в ней. Нельзя приписывать весь результат этому кейсу.

Смысл:
- показатель продолжительного просмотра, а не активного чтения;
- 120 секунд — начальный рабочий порог, не подтвержденный исследованием норматив.

Замечание:
- отсутствие этого события не равно провалу кейса;
- для короткого или очень структурного сценария пользователь может считать контент полезным без 120 секунд просмотра.

### 6.9 `short_mode_toggle_on`
Срабатывает на включение сокращенного режима.

Смысл:
- adoption ключевой feature.

### 6.10 `short_mode_toggle_off`
Срабатывает на возврат в полный режим.

Смысл:
- short mode может выступать entry point в полный кейс;
- само по себе событие не является ни положительным, ни отрицательным без контекста.

### 6.11 `image_fullscreen_open`
Срабатывает на открытие media в fullscreen.

Смысл:
- показатель ценности визуального слоя и интереса к деталям кейса.

### 6.12 `view_about`
Срабатывает при открытии страницы `About`.

Смысл:
- вторичный signal of professional interest.

## 7. Key Scenarios

### 7.1 Home Engagement Scenario
Сценарий:

`view_home -> home_preview_open -> home_preview_change -> click_case_card`

Смысл:
- проверить, замечают ли пользователи механику главной;
- исследуют ли ее;
- помогает ли она открыть кейс.

### 7.2 Case Exploration Scenario
Сценарий:

`view_case -> view_second_case`

Смысл:
- определить, вызывает ли один кейс интерес к следующим.

### 7.3 Глубокий и продолжительный просмотр
Сценарий:

`view_case -> case_scroll_90 and/or case_read_120s`

Смысл:
- отдельно оценивать глубокую прокрутку и продолжительность просмотра за визит;
- не считать эти сигналы доказательством чтения и понимания.

### 7.4 Short Mode Scenario
Сценарий:

`view_case -> short_mode_toggle_on -> next outcome`

Допустимые следующие outcomes:
- `short_mode_toggle_off`
- следующий `view_case` с другим `case_slug`
- `view_about`
- `image_fullscreen_open`
- нет следующего отслеженного действия до конца визита

Смысл:
- short mode оценивается не только по adoption, но и по распределению исходов после включения.
- Для исхода «другой кейс» используется `view_case`, а не одноразовое `view_second_case`: переход к третьей работе тоже должен учитываться.
- Отсутствие следующего события не доказывает выход или потерю интереса.

### 7.5 Fullscreen Media Scenario
Сценарий:

`view_case -> image_fullscreen_open`

Смысл:
- понять, воспринимаются ли визуальные материалы как достаточно ценные для детального просмотра.

## 8. Derived Metrics
Метрики сгруппированы по двум продуктовым вопросам: качество вовлечения (кейсы, About) и использование функций (превью, Short Mode, fullscreen).

`V(A)` — число визитов Метрики с событием A. `V(A → B)` — число визитов, в которых B произошло после A. В пределах одного числителя визит учитывается один раз. Повторные клики не увеличивают долю. `OR` означает объединение визитов без двойного счета. Все числители и знаменатели используют один период и одинаковые фильтры; при нулевом знаменателе результат «нет данных», а не 0%.

Для цепочки недостаточно наличия обоих событий в визите: необходим порядок. Проверять его следует в воронке/составной цели с подходящими условиями либо по данным с порядком событий. Агрегированные количества достижений не восстанавливают последовательность. Для сценариев функций внутри кейса действия сопоставляются с соответствующей страницей; About должен быть открыт после кейса.

### 8.1 Home Metrics

#### Активация превью (`Home Preview Open Rate`)
Формула:

`V(view_home → home_preview_open) / V(view_home)`

Смысл:
- доля визитов с главной, в которых затем было активировано превью.

#### Исследование превью (`Home Preview Exploration Rate`)
Формула:

`V(home_preview_open → home_preview_change) / V(home_preview_open)`

Смысл:
- насколько часто первое касание preview переходит в исследование нескольких preview.

#### Переходы с главной в кейсы (`Case Card Click Rate`)
Формула:

`V(view_home → click_case_card) / V(view_home)`

Смысл:
- насколько эффективно главная ведет к открытию кейса.

### 8.2 Case Metrics

#### Открытие кейса после главной (`Case Open Rate`)
Формула:

`V(view_home → view_case) / V(view_home)`

Смысл:
- доля визитов с главной, где после нее открылся кейс; прямой вход в кейс не включается в числитель без предшествующей главной.

#### Доля визитов с несколькими кейсами (`Multi-Case Rate`)
Формула:

`визиты с двумя или более уникальными case_slug из view_case / V(view_case)`

Смысл:
- доля визитов с кейсами, в которых открыта хотя бы еще одна уникальная работа.
- Практическое приближение для интерфейса без подробной выгрузки: `V(view_second_case) / V(view_case)`. Подписывать как «сигнал нескольких кейсов в одной вкладке»: границы локальной сессии и визита Метрики могут различаться.

#### Среднее число уникальных кейсов за визит (`Average Unique Cases`)

`сумма числа уникальных case_slug в каждом визите с кейсами / V(view_case)`

Визиты без кейсов исключаются. Повторы, reload и возвраты к тому же slug не увеличивают число уникальных работ. Нельзя делить все достижения `view_case` на число визитов и называть результат уникальными кейсами. Для точного расчета нужны связанные с визитом события/просмотры и slug, а не только суммарные достижения из CSV или PDF.

#### Доля глубокого скролла (`Deep Scroll Rate`)

`V(view_case → case_scroll_90) / V(view_case)`

Сигнал достижения 90% прокрутки хотя бы одного полного кейса за визит.

#### Доля продолжительного просмотра (`Sustained View Rate`)

`V(view_case → case_read_120s) / V(view_case)`

Доля визитов с достижением локального суммарного порога 120 секунд. Это не среднее время и не доля доказанного чтения.

#### Доля глубокого или продолжительного просмотра (`Deep Read Rate`, историческое имя)
Формула:

`V(view_case → (case_scroll_90 OR case_read_120s)) / V(view_case)`

Смысл:
- объединенный показатель вовлечения; визит с обоими сигналами учитывается один раз;
- в отчете сохраняются и две отдельные доли, чтобы не смешивать скролл с длительностью.

### 8.3 Short Mode Metrics

#### Использование краткого режима (`Short Mode Adoption Rate`)
Формула:

`V(view_case → short_mode_toggle_on) / V(view_case)`

Смысл:
- как часто пользователи вообще включают short mode.

#### Возврат к полной версии (`Short Mode Return-to-Full Rate`)
Формула:

`V(short_mode_toggle_on → short_mode_toggle_off на том же кейсе) / V(short_mode_toggle_on)`

Смысл:
- как часто short mode становится входом в полный кейс.

#### Дальнейшие действия после краткого режима (`Short Mode Outcome Distribution`)
Формула:

Для каждого визита берем первое включение `short_mode_toggle_on` после открытия кейса и первое следующее подходящее действие до конца визита. Один визит относится ровно к одному исходу:
- `short_mode_toggle_off`
- `view_case` с другим slug
- `view_about`
- `image_fullscreen_open`
- `no tracked follow-up`

`визиты с данным первым исходом / визиты с первым включением краткого режима`. Повторное включение не создает новый знаменатель. Возврат к полной версии и fullscreen сопоставляются с кейсом включения. Если порядок или привязка к странице неизвестны, распределение не вычисляется. Сумма известных исходов и «нет отслеженного продолжения» — 100% при полном наборе данных.

Смысл:
- основной способ анализа полезности short mode.

### 8.4 Fullscreen Metrics

#### Полноэкранный просмотр медиа (`Fullscreen Open Rate`)
Формула:

`V(view_case → image_fullscreen_open на странице кейса) / V(view_case)`

Смысл:
- как часто case visits приводят к детальному просмотру media.

### 8.5 About Metrics

#### Переход к информации об авторе (`About View Rate`)
Формула:

`V(view_case → view_about) / V(view_case)`

Смысл:
- как часто после кейса пользователь переходит к странице `About`.

## 9. Composite Interpretation Layer
Для ручного анализа нужно использовать и более простые интерпретационные слои.

### 9.1 `Home Interaction Signal`
Считается положительным, если в рамках визита был хотя бы один из signals:
- `home_preview_open`
- `home_preview_change`
- `click_case_card`

### 9.2 `Deep Case Engagement Signal`
Русское название: «Расширенное вовлечение в портфолио». Не является доказательством глубокого чтения.

Считается положительным, если в рамках визита был хотя бы один из signals:
- `view_second_case`
- `case_scroll_90`
- `case_read_120s`
- `view_about` после `view_case`

### 9.3 `Feature Usage Signal`
Считается положительным, если в рамках визита был хотя бы один из signals:
- `short_mode_toggle_on`
- `image_fullscreen_open`

## 10. Interpretation Rules

### 10.1 General Rule
На низком объеме трафика нельзя опираться на проценты как на устойчивый вывод.

При малом числе визитов приоритет анализа:
1. наличие события вообще;
2. соотношение `goal visits` и `goal completions`;
3. динамика по неделям;
4. только потом conversion rate.

### 10.2 `Goal Completions`
`Достижения цели` в Метрике:
- сколько раз событие произошло вообще;
- не равно числу пользователей;
- не равно числу визитов.

### 10.3 `Goal Visits`
`Целевые визиты` в Метрике:
- сколько визитов содержали хотя бы одно достижение цели.

### 10.4 `Conversion`
`Конверсия` в Метрике:
- доля визитов, в которых цель была достигнута.

На малом объеме трафика:
- не использовать как главный ориентир;
- рассматривать только как вспомогательную долю.

### 10.5 Short Mode Rule
`short_mode_toggle_on -> exit`
не должен автоматически интерпретироваться как негативный исход.

Правильный анализ:
- смотреть на распределение исходов;
- сравнивать долю `return-to-full`, `next-case`, `about`, `fullscreen`, `exit`;
- делать вывод только по относительной структуре сценариев.

### 10.6 Home Preview Rule
`home_preview_open` сам по себе не доказывает ценность механики главной.

Правильный анализ:
- `home_preview_open` отвечает за заметность;
- `home_preview_change` отвечает за исследование;
- `click_case_card` отвечает за переход в содержательный сценарий.

## 11. Recommended Reporting Layers

### 11.1 Manual Layer in Metrica
Для интерфейса Метрики цели должны быть сгруппированы по блокам:

#### Home
- `view_home`
- `home_preview_open`
- `home_preview_change`
- `click_case_card`

#### Cases
- `view_case`
- `view_second_case`
- `case_scroll_90`
- `case_read_120s`

#### Features
- `short_mode_toggle_on`
- `short_mode_toggle_off`
- `image_fullscreen_open`
- `view_about`

### 11.2 Ручной weekly-анализ
Автоматические отчеты и отдельный pipeline не создаются. Для ручного анализа нужно собирать и сопоставлять:
- raw counts;
- goal visits;
- conversion where useful;
- derived metrics из раздела 8;
- interpretation layer из раздела 9.

## 12. Minimum Weekly Analysis Structure

### 12.1 Raw Events Section
Для каждого source event:
- event name;
- total completions;
- goal visits;
- conversion;
- period.

### 12.2 Derived Metrics Section
Для каждой derived metric:
- metric name;
- formula;
- numerator;
- denominator;
- result;
- interpretation note.

### 12.3 Summary Section
Краткая weekly-summary структура должна отвечать на вопросы:
- замечают ли главную механику;
- открывают ли кейсы;
- исследуют ли больше одного кейса;
- есть ли глубокая прокрутка и продолжительный просмотр;
- используется ли short mode;
- используется ли fullscreen;
- есть ли интерес к `About`.

## 13. Recommended Data Transfer Format
Для weekly-анализа предпочтителен один из форматов:
- PDF-отчет из Метрики;
- CSV-экспорт из Метрики;
- набор скриншотов по ключевым блокам.

Если данных мало и анализ короткий, достаточно:
- PDF weekly report;
- или 2-4 скриншотов по блокам `Home`, `Cases`, `Features`.

Таких агрегатов достаточно для количества достижений и целевых визитов, но недостаточно для точного среднего числа уникальных кейсов и распределения следующих действий. Эти метрики оставлять «нет данных», пока нет подходящего отчета или детальной выгрузки. Не восстанавливать их из суммарных счетчиков.

### 13.1 Действия в кабинете после публикации изменений

Идентификаторы всех 12 событий сохранены. Уже настроенные цели не удалять и не пересоздавать. Проверить соответствие идентификаторов разделу 5: тип «Целевое событие» (ранее JavaScript-событие), условие «совпадает». Создать только отсутствующие цели.

Рекомендуемые подписи измененных сигналов:
- `view_second_case` — «Второй уникальный кейс — сигнал вкладки»;
- `case_scroll_90` — «Скролл полной версии — 90%»;
- `case_read_120s` — «Продолжительный просмотр кейсов — 120 секунд».

Проверить таймаут визита счетчика: локальный таймаут — 30 минут. Даже при совпадающем значении многовкладочные визиты и правила Метрики не делают локальную сессию равной визиту. Не менять счетчик автоматически ради совпадения.

В отчетах записать фактическую дату публикации этой версии. После нее изменяются семантика времени и дедупликация второго кейса, а первый `hit` перестает пропускаться. Старые и новые периоды напрямую не сравнивать; исторические достижения не пересчитываются кодом сайта. Пока изменения не опубликованы, новая семантика относится только к локальной версии.

Источники настройки: [Целевое событие](https://yandex.ru/support/metrica/ru/general/goal-js-event), [Определение визита](https://yandex.ru/support/metrica/ru/general/glossary), [Настройка SPA-счетчика](https://yandex.ru/support/metrica/ru/code/counter-spa-setup).

## 16. Проверки реализации

`node --test tests/analytics/*.test.mjs` (Node.js с native TypeScript stripping, проверено на v24.14.1) проверяет локальную сессию, уникальные кейсы, сохранение/истечение/недоступность storage, порог времени, паузы, смену режима и страницы, а также первый и последующие `hit`. Для эффектов React используется mock-окружение; эти тесты не подтверждают прием событий реальным счетчиком.

`pnpm typecheck` также проверяет compile-only контракт в `tests/analytics/events.typecheck.ts`: неизвестное событие, пропущенный payload и неверные типы параметров должны отклоняться TypeScript.

Перед сдачей выполняются общий lint и production build; маршруты проверяются в static export. Проверка поступления целей в рабочую Метрику выполняется после публикации, отдельно от локальных тестов. Визуальные изменения в эту задачу не входят.
