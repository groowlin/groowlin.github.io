# Portfolio Case MDX Structure

## 1. Purpose
Единый контракт контента для кейсов в формате `MDX + frontmatter`.

## 2. Storage
- Directory: `content/work`
- File pattern: `${slug}.mdx`
- Source of truth for home list and `/work/[slug]`: frontmatter каждого кейса.

## 3. Frontmatter Contract
Обязательные поля:
- `slug: string`
- `title: string`
- `subtitle: string`
- `status: "published" | "hidden"`
- `preview: { kind, aspectRatio, src?, placeholderToken?, centered? }`
- `description: string`
- `canonical: string` — обязательное compatibility-поле frontmatter; текущий work-loader не использует его значение и вычисляет runtime canonical как `/work/${slug}`.

Опциональные поля:
- `ogImage: string`
- `ogType: "article" | "website"`
- `shortSummary: { paragraphs: string[]; media?: MediaPlaceholder[] }`

### `subtitle` rules

`subtitle` отображается в заголовке страницы кейса. На главной период из него используется для группировки годовой скобки; вместо роли/формата текущая строка метаданных показывает renderer-owned `HOME_METRIC_LABELS`, в виде групп без разделителей.
Отдельное поле для главной не добавляется.

Формат:

`period · role/format/status`

Примеры:

- `2024-2025 · Продуктовый дизайн`
- `2025 · Продуктовый дизайн`
- `2023-2024 · UX/UI дизайн`
- `2025-2026 · Продуктовый дизайн`

Ограничения:

- не длиннее паттерна `2023–2024 · продуктовый дизайн`;
- не дублировать продуктовый hook из `title`;
- использовать для периода, роли, формата или статуса кейса;
- продуктовый эффект раскрывать в `title`, первом narrative-блоке и body кейса, а не в `subtitle`.

### `shortSummary` rules

`shortSummary` — опциональная короткая версия кейса для второго уровня пирамиды Минто.
Это не teaser, не SEO-description и не отдельная страница, а сжатый паспорт решения внутри самого кейса.

Правила:

- `shortSummary.paragraphs` содержит 1-4 абзаца;
- рекомендуемый формат для паспортной версии: `Проблема`, `Решение`, `Ожидаемый эффект`;
- для крупных или мета-кейсов допустима индивидуальная структура короткой версии, если она плотнее и точнее передает продуктовую логику кейса;
- паспортные лейблы пишутся внутри строки `paragraphs`, а не как отдельные MDX-заголовки или новые frontmatter-поля;
- для паспортной структуры можно использовать multiline YAML через `|`; переносы внутри строки рендерятся short-summary UI;
- `shortSummary.media` опционально содержит медиа после текстового блока короткой версии;
- абзацы должны опираться только на полный текст кейса;
- short-метрики раскрывают направление эффекта и краткую связь с решением, а не просто перечисляют показатели. Полученный эффект называют по авторским основаниям; целевой — через «цель» или «ожидаемый рост/снижение». Масштаб («значительный», «существенный», «резкий», проценты) без подтверждения не добавляется; RR сохраняет конкретное окно D7/D30;
- ожидаемый эффект не представляется полученным результатом; служебные пометки о статусе данных в публичный текст не добавляются;
- поле не заменяет `description`; на главной из него используется только тело точного раздела `Мой вклад` как подпись hover-превью, без самого лейбла;
- если у кейса нет `shortSummary`, переключатель короткой версии не показывается.

Производная подпись главной: `getHomeWorkEntries()` находит элемент `shortSummary.paragraphs`, у которого первая строка после trim равна строго `Мой вклад`, и передаёт непустое тело остальных строк как `HomeWorkEntry.previewCaption`. Это renderer DTO, а не новое frontmatter-поле; схема и исходный текст не расширяются. Если раздел отсутствует или пуст, подпись не выводится; `Решение`, `Решения` и другие разделы не подставляются. Будущие кейсы с декоративным donor-preview подпись не наследуют. Геометрия и анимация подписи заданы в [Home showcase motion](../../design-system-spec.md#home-showcase-motion).

Утверждённый overview: четыре отдельных элемента `shortSummary.paragraphs` с непустым содержанием и точными первыми строками одного из двух наборов в указанном порядке: Medicine/Familia/Zvuk/Golden Apple — `Контекст`, `Метрики`, `Мой вклад`, `Ограничение`; Portfolio — `Продуктовая задача`, `Решения`, `Аналитика и развитие`, `Автоматизация и AI`. Используется multiline YAML `|`. Только точное совпадение одного набора включает общий существующий semantic `dl/dt/dd` renderer; остальные форматы сохраняют прежний рендер. Текст предшествует существующим media. «Ограничение» называет предметную границу решения, а не служебную оговорку о данных. Medicine — ориентир только по краткости короткого режима, не по структуре полного рассказа других кейсов. Ориентир short — до 60–75 слов: задача, личный вклад и продуктовая ценность без пересказа процесса. Portfolio сохраняет все четыре short-раздела: «Продуктовая задача», «Решения», «Аналитика и развитие», «Автоматизация и AI». Разрешено сократить их суммарно примерно до 50–60 слов с целью чтения 15 секунд; это редакционная цель, не измеренное время. В полном режиме разрешено компактно пояснить ER/FA/CD в существующем разделе аналитики; остальной рассказ и media сохраняются. VK сохраняет индивидуальную структуру paragraphs. Сетка, типографика и отступы заданы в [ДС — Semantic text usage](../../design-system-spec.md#semantic-text-usage).

### Редакционная опора и показатели кейсов

Опора — авторские данные, исходные версии и история кейса. В публичном тексте нет пометок об учебных, тестовых, неподтверждённых данных или редакционной модели. Результат проектирования можно раскрывать через изменение сценария и его пользу; ожидаемый эффект — естественной формулировкой. Это не разрешает выдумывать новые численные измерения, исследования, эксперименты или представлять ожидаемый рост полученным. Количество показателей определяется логикой и полезностью, без обязательного набора из трёх; в полном тексте объясняется связь каждого показателя с решением.

Во full, short и renderer-owned `HOME_METRIC_LABELS` на главной показатели называются общепринятыми аббревиатурами. При первом упоминании в полном тексте допустима расшифровка; обычное описание сценария остаётся прозой. На главной перед каждой метрикой отображается декоративная иконка роста по [ДС](../../design-system-spec.md#home-showcase-motion), без процентов и заявления о фактическом измеренном росте. Исключение Portfolio сохраняет прежние авторские ER · FA · CD без изменения смысла. Расшифровки и сценарный смысл заданы в профильных определениях; подпись сама по себе не заявляет результат замера. Для сохранений и прослушиваний новые сокращения не вводятся: действия раскрываются в сценарии и обосновании RR обычной прозой, без оформления отдельной метрикой. Авторские ER/FA/CD Portfolio раскрываются по [словарю аналитики](portfolio-analytics-metrics-spec.md#80-отображаемые-обозначения-portfolio). Канонические наборы и основания:

| Кейс | Подписи главной | Смысл и связь с решением |
| --- | --- | --- |
| Portfolio | ER · FA · CD | Авторские обозначения групп существующих показателей; определения и связи с аналитикой — только в [каноническом словаре](portfolio-analytics-metrics-spec.md#80-отображаемые-обозначения-portfolio). Новые формулы, события и результаты замеров не добавляются. |
| Globus | CR · RR D30 · NPS | Восстановлены прежние авторские подписи: CR (Conversion Rate) — конверсия; RR D30 (Retention Rate, Day 30) — доля впервые использовавших сценарий, вернувшихся к нему на 30-й день; NPS (Net Promoter Score) — готовность рекомендовать. Они не добавляют в status-кейс новые цифры, целевые действия или результаты замеров. Кейс ожидания релиза и отсутствие краткого режима сохраняются. |
| Medicine | CR · CSAT · AOV | CR (Conversion Rate) — конверсия в корзину; CSAT (Customer Satisfaction Score) — удовлетворённость; AOV (Average Order Value) — средний чек. Конверсия в корзину — переход от просмотра услуги к добавлению; удовлетворённость (CSAT) — оценка пользовательского опыта; средний чек (AOV) — сумма заказа. Фото до/после поддерживают выбор, видео и ответы врача объясняют процедуру, варианты и сочетание процедур помогают собрать заказ. Автор подтвердил качественный рост: конверсия в корзину после первой и третьей итераций, CSAT после второй, AOV за счёт третьей; также подтверждён общий рост конверсии в заявку. Новых чисел и методик не добавлять. |
| Familia | RR D30 | RR D30 (Retention Rate, Day 30) — доля впервые использовавших сценарий, вернувшихся к полезному использованию на 30-й день. Сохранения — отложенные находки для продолжения выбора; повторное использование — возвращение к находкам, подпискам и информации о товаре. Сканер, размер и отправка поддерживают офлайн-выбор; кабинет, лояльность, подписки и сторис — продолжение между визитами. Конверсии и Activation в кейсе нет. Подарочные карты — отдельный сценарий подарка, без заявления выручки. |
| Golden Apple | CR · RR D7 | CR (Conversion Rate) — переход из примерки в добавление примеряемого товара в корзину; RR D7 (Retention Rate, Day 7) — доля впервые использовавших примерку, вернувшихся к ней на седьмой день. Добавления примеряемого товара в корзину связывают примерку с выбором; возвраты к примерке — её использование при следующем выборе. Настроение помогает начать, подсказки о свете и ракурсе — сравнить оттенки, AI-чат — получить совет и вернуться к товару. CSAT и новый фактический рост не добавляются. |

Шаринг публичных профилей и подборок создаёт внешний вход новым пользователям, без заявления измеренного притока. Прослушивания из профиля — запуски музыки из треков и подборок человека. Новые значения, периоды и атрибуция не добавляются.

Обозначение TCT соответствует [исследованию времени выполнения UX-задач в PLOS ONE](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0280400). RR обязателен с конкретным окном D7 или D30 во full, short и home. RR D7/D30 означает возврат ровно на день 7/30 (Return On), а не в любой день периода. Окна оценки выбраны по цели решения: Golden Apple D7 — повторный выбор через примерку, Familia D30 — продолжение полезного использования между офлайн-визитами; Zvuk D7 и Globus D30 сохраняются. Это выбор срока оценки, не утверждение об измеренном ритме использования. Определение Return On и отличие от интервального удержания — в [Amplitude](https://amplitude.com/books/mastering-retention/the-retention-lifecycle-framework); связь окна с usage interval — в [документации Amplitude](https://www.amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-interpret-usage).

Архивы исходных текстов остаются вне публикуемой коллекции: `docs/archive/cases/medicine-before-2026-10-05.mdx`, `familia-before-2026-10-08.mdx`, `goldenapple-before-2026-10-08.mdx`, `zvuk-before-2026-10-08.mdx`. Исходные исследования и решения сохраняются без новых выборок. Slug, title, subtitle, status и пути media не меняются.

Редакционная цель согласуется с рекомендациями [NN/g о портфолио и найме](https://www.nngroup.com/articles/ux-hiring-insights/): объяснять вклад понятно читателям за пределами дизайна; [NN/g о количественных кейсах](https://www.nngroup.com/articles/quantifying-case-study/): выбирать одну или несколько метрик по существенным аспектам опыта, а не ради одинакового количества.

Правила media:

- при текстовой редактуре не удалять прежние full/short media без прямого запроса пользователя; сохранять существующие src, props и captions;
- Zvuk сохраняет full-media в порядке `main.png` → `4_gallery_1.png` → `4_gallery_2.png` → `5_gallery_1.png`; short-media — `short-profile.png` → `short-player.png`. Профили остаются основным направлением, плеер — поддерживающим разделом перед итогом; подписи full/short/home — `RR D7 · NU`.

- `shortSummary.media` использует тот же `MediaPlaceholder[]`, что и MDX media;
- assets для короткой версии должны лежать внутри media-папки своего кейса (`public/media/cases/{slug}/...`);
- отдельная подпапка для short-assets не является обязательной частью контракта;
- имена файлов должны быть уникальными и не конфликтовать с основными assets кейса: например `short-before.png`, `short-after.png`, а не повторные `before.png`, `after.png`;
- captions пишутся как обычные подписи media; для пар до/после использовать `Было` и `Стало`.

## 4. Body Contract
- MDX body — это основной контент кейса.
- Разрешены стандартные markdown-блоки и встраиваемые MDX-компоненты из `lib/content/mdx-components.tsx`.
- Поддерживаются `<Media />`, MDX-компонент `<Gallery> ... </Gallery>` с вложенными `<Media />` и специализированный `<PortfolioMotionDemo />` для кейса `portfoliocase`.
- Для `<Gallery />` встроено fullscreen-открытие media по клику или тапу только внутри самого gallery-блока.
- Для отдельного media внутри `<Gallery />` fullscreen можно отключить через `openable={false}`.
- `<PortfolioMotionDemo />` не принимает props, не содержит интерактивных элементов и рендерит статичный репрезентативный кадр при reduced motion.
- Полный MDX и короткий renderer-slot используют одну lightweight-точку входа demo; scene runtime загружается у существующей playback-границы видимости, сохраняя layout/reveal shell. Галерея и modal renderer разделены без изменения данных кейса. Каноническое правило: [ДС — Client runtime loading](../../design-system-spec.md#client-runtime-loading).
- Renderer может передать типизированный case-specific `shortAfterContent`-slot. Он рендерится только в short-ветке после всего текста и `shortSummary.media`, не является частью frontmatter-контракта и не требует отдельного контентного поля. Для `portfoliocase` slot содержит тот же `<PortfolioMotionDemo />`, что используется в полном MDX-контенте; full- и short-экземпляры взаимоисключающие и одновременно не монтируются.
- Цикл `<PortfolioMotionDemo />` активен только в пределах viewport с `rootMargin: "100px 0px"`, при видимом документе и без `prefers-reduced-motion`. Вне активной области таймеры и motion-слои останавливаются, индекс дискретной сцены сохраняется, а после возврата воспроизведение продолжается со следующей сцены без восстановления промежуточного прогресса перехода.

## 5. Motion Contract
- Motion не задаётся через frontmatter и не настраивается из MDX-контента.
- `/work/[slug]` использует общесистемный page-reveal для header и MDX-блоков через `SiteShell` + `PageRevealSequence`.
- Для этого page-reveal зафиксирован единый renderer-level motion contract:
  - `opacity + blur` и `translateY` анимируются раздельно;
  - `opacity + blur` используют `0.7s` и `cubic-bezier(0.22, 1, 0.36, 1)`;
  - `translateY` использует `1.12s`, `cubic-bezier(0.18, 0.88, 0.28, 1)` и стартовый offset `28px`;
  - stagger остаётся общесистемным: `calc(var(--page-reveal-index, 0) * 80ms)`.
- Media внутри `Gallery` используют системное fullscreen motion-поведение:
  - переход из thumbnail в modal bounds и обратно;
  - backdrop fade/blur;
  - reduced-motion fallback без анимации.
- `PortfolioMotionDemo` является контентной демонстрацией уже существующих интерфейсных состояний, а не системным page-level motion-паттерном. Общий ритм замедлен в `1.2x`: outgoing проходит `0 -> 120px` за `720ms` по `cubic-bezier(0.7, 0, 0.84, 0)`, а incoming достигает верхней точки на границе lifecycle `1440ms` по зеркальной `cubic-bezier(0.16, 1, 0.3, 1)`. Outgoing opacity остаётся `1`, а blur — `0px`, пока не пройдены первые `60px`; затем они меняются до `0` и `18px`. Incoming начинает полёт при outgoing opacity `0.5` примерно на `683ms`; к первым `60px` подъёма примерно на `760ms` он уже достигает opacity `1` и blur `0px`. Равная видимость сцен составляет около `24.4% / 24.4%`, ниже лимита `30% / 30%`. Каждая сцена проходит rotation через `0deg` в противоположную сторону: `-15deg -> 0deg -> 15deg` или `15deg -> 0deg -> -15deg`; стартовое направление чередуется между сценами и через стык цикла. Внутренняя production-анимация запускается через guard при opacity `>= 0.8`; top card один раз переключается `to-profile -> to-home`, short mode остаётся в масштабе `2x`, и обе смены состояния начинаются после задержки `280ms`. Иконки top card в обоих состояниях постоянно воспроизводят production hover-cycle `620ms`. Top card сохраняет desktop-ширину `--home-top-card-width` на всех viewport. Сцена кейса содержит только `Портфолио как продукт`: его bubble сохраняет естественные production-пропорции по текстовому содержимому, целиком масштабируется в `1.2x` и центрируется внутри сцены; вместе с ним пропорционально увеличиваются текст, стикер, скругление, тени и визуальная амплитуда деформации пузыря. Этот кейс объединяет подъём и падение в одну непрерывную траекторию без зависания в верхней точке; opacity и blur меняются после первых `60px` каждого участка. Стеклянный пузырь закреплён за кейсом и после его проявления появляется с задержкой `140ms`: opacity меняется за `280ms`, а scale проходит `0.1 -> 1` с пружинным хвостом `220 / 14 / 1`; затем запускается sticker frame-cycle. Viewport использует высоту `calc(--layout-preview-size - --space-4xl - --space-2xl)` (`412px`), а центр сцены смещён вверх на `68.8px`: верхняя точка находится на линии верхней трети (`≈137.2px` при целевых `≈137.3px`), при этом снизу остаётся полный запас под падение, поворот, blur-хвост и масштаб кейса без обрезания. Каждая завершившая exit-сцена вызывает `safeToRemove` через `720ms`, поэтому циклический ключ не переиспользует экземпляр с уже изменёнными motion values. Visibility-aware timeout останавливает цикл при скрытии документа и пересоздаёт одну presence-сессию после возврата, исключая накопление exit-слоёв. Reduced-motion fallback остаётся статичным и не запускает цикл.
- Отдельные кейсы не должны вводить собственные motion-правила поверх этих паттернов без изменения дизайн-системы.

## 6. Publication Rules
- `published`:
  - показывается на `/`
  - доступен на `/work/[slug]`
- `hidden`:
  - не показывается на `/`
  - недоступен на `/work/[slug]`

## 7. Validation and Loading
- Frontmatter валидируется через Zod (`lib/content/schemas.ts`).
- Metadata title наследуется из общего layout; frontmatter title выводится в контенте страницы. Description берётся из frontmatter, canonical вычисляется из slug.
- Reveal-ready определяется завершением opacity/filter visibility-трека, а не движения; all-animation waiting относится только к cleanup.
- Контент читается из файловой системы (`lib/content/work.server.ts`).
- MDX рендерится server-side через `next-mdx-remote/rsc`.
