# AGENTS.md

## 1) Цель проекта
Поддерживать персональное портфолио продуктового дизайнера на статической архитектуре:
- контент хранится в репозитории (`MDX + frontmatter`),
- сайт собирается через Next.js static export,
- публикация идет на GitHub Pages.

Целевая IA:
- `/`
- `/work/[slug]`
- `/about`

## 2) Текущее состояние (актуально на 2026-03-26)
Соответствие целевой архитектуре: `~100%`.

Что уже реализовано:
- CMS/admin/API удалены.
- Supabase и NextAuth удалены.
- Контент переведен на MDX-файлы.
- Включен `output: "export"`.
- Добавлен GitHub Pages workflow.

## 6) Контентная модель (обязательно)
- Источник основного авторского контента: `content/**/*.mdx`.
- Новый контент кейсов и статических страниц добавлять через frontmatter + MDX body. Renderer-owned строки интерфейса и подписи показателей главной (`HOME_METRIC_LABELS`) остаются в компонентах; на главной используются общепринятые аббревиатуры со значениями в каноническом контракте; Portfolio сохраняет ER · FA · CD; разрешены сокращение четырёх существующих short-разделов до цели чтения 15 секунд и компактное пояснение метрик в существующем full-разделе аналитики, остальной рассказ и медиа сохраняются; подписи сами по себе не заявляют измеренный результат. Набор определяется смыслом кейса, без фиксированного количества; RR во full/short/home всегда содержит конкретное окно D7 или D30; канонические определения и основания — в `docs/specs/portfolio-case-json-structure.md`. Публичные тексты не содержат служебных пометок об учебных, тестовых, неподтверждённых данных или редакционной модели. Опора — авторские данные и история; новые численные измерения и фактический рост не выдумывать. Medicine — ориентир только по краткости short, не по структуре полных кейсов.
- Контракт frontmatter валидируется через Zod.
- Metadata страницы должна иметь `title`, `description`, `canonical`; `title` наследуется из глобального layout, а description и canonical задаются на уровне страницы. Общий Open Graph/Twitter preview загружается из `content/site/link-preview.mdx`.
- Canonical кейса вычисляется как `/work/${slug}`; обязательное поле `canonical` в его frontmatter сохраняется для совместимости контракта и не переопределяет вычисленный путь.

## 7) Ограничения архитектуры
- Проект статический: нельзя добавлять server actions, runtime API routes, DB-зависимости.
- Не возвращать CMS/admin-панель без отдельного явного запроса.
- `next.config.mjs` должен оставаться совместимым с GitHub Pages (`output: "export"`, `trailingSlash: true`).
- Интерактивность главной (hover + preview-pane) сохраняется, если нет отдельного запроса на редизайн.

## 9) Обязательный порядок сдачи изменений
1. Сразу синхронизировать затронутые разделы ДС, спецификаций и структурных JSON в той же правке; не оставлять актуализацию документов отдельной будущей задачей.
2. До запуска любой проверки или теста определить характер изменения по разделу 10. Запуск допустим только при конкретном возможном влиянии на сборку; сам факт правки файла не является таким основанием.
3. Для UI-правок и правок только документации проверки и тесты не выполнять: не запускать typecheck, lint, build, unit/integration/e2e-тесты, browser smoke-test или визуальную проверку.
4. Для остальных изменений с влиянием на сборку выполнить только применимые команды из раздела 10 и относящиеся к изменению существующие тесты. При изменении маршрутов/export дополнительно проверить затронутые маршруты и отсутствие `admin/api/preview` в полученной статике.
5. В итоговом отчете перечислить реально выполненные проверки и тесты; если они не запускались, указать причину. Не заявлять результат проверенным на основании одного чтения исходников.

## 10) Строгая политика запуска проверок и тестов
- Эта политика имеет приоритет над прежними чеклистами и требованиями запуска проверок в остальных документах проекта.
- Документация, ДС, спецификации, описательные структурные JSON и обычные текстовые правки MDX: проверки и тесты не запускать.
- UI-правки (цвета, шрифты, размеры, отступы, скругления, CSS, визуальная разметка компонентов, анимации, hover/focus, drag и другие интерфейсные взаимодействия): проверки и тесты не запускать. Изменение `ts/tsx/js` UI-компонента само по себе не требует typecheck или lint. Визуальную оценку выполняет пользователь.
- Проверки и тесты для остальных правок разрешены и обязательны только при конкретном возможном влиянии на сборку: зависимости, импорты/разрешение модулей, build-конфигурация, статическая генерация, маршруты/export/deploy, парсинг MDX или контракт данных, используемый сборкой. В отчете назвать этот механизм, а не общее предположение «любая правка может сломать сборку».
- Если изменение может нарушить MDX-парсинг, frontmatter, slug или разрешение media/контентных путей при сборке: выполнить `pnpm build` и только относящиеся к этому изменению существующие тесты.
- Если меняются используемые сборкой контентные схемы, типы или загрузчики: выполнить `pnpm typecheck`, `pnpm build` и релевантные существующие тесты.
- Если меняются зависимости, разрешение модулей, маршруты, metadata-генерация, конфигурация Next.js или export/deploy-логика: выполнить применимые `pnpm typecheck`, `pnpm lint`, `pnpm build` и релевантные существующие тесты. Не расширять проверки на несвязанные области.
- Для смешанной правки основанием служит только отдельное изменение, влияющее на сборку; UI-часть не запускает дополнительные проверки или тесты.
- Сдача, PR, коммит или деплой сами по себе не являются основанием для полного набора проверок. Не запускать их «на всякий случай», для повторного подтверждения уже полученного результата или из-за изменения UI.
- Чтение исходников и документов, редактирование и просмотр diff для согласования правки допустимы; это не означает разрешение запускать валидаторы, тесты, сборку, browser smoke-test или визуальную проверку.

## 12) Правила дизайн-системы и структуры (обязательно)
1. Never invent spacing values.
2. Follow component structure and use tokens from `design-system-spec.md`.
3. If something conflicts with design tokens, tokens win.
4. Самостоятельное изменение дизайн-системы вне согласованного запроса требует явного разрешения пользователя. Если изменение UI/поведения или актуализация ДС уже разрешены пользователем, это разрешение распространяется на необходимую синхронизацию соответствующих документов; повторное разрешение на ту же синхронизацию не запрашивать.
5. Любая согласованная правка UI, токенов, структуры, анимаций, контентного контракта или поведения должна сразу сопровождаться актуализацией затронутого раздела `design-system-spec.md`, профильных `docs/specs` и обоих структурных файлов (`portfolio-structure.json`, `portoflio-structure.json`), если они описывают изменяемое правило. Делать это в одной правке/коммите, до сдачи результата.
6. Перед изменением сопоставить запрос с действующим контрактом ДС. При конфликте не придумывать новое правило: использовать уже данное разрешение пользователя либо согласовать изменение до реализации. Новая формулировка заменяет прежнюю во всех затронутых документах; не оставлять противоречащие обязательные требования.
7. ДС является нормативным UI-контрактом, профильные спеки задают контентные и компонентные контракты. Численные значения и общие правила не дублировать независимо: в профильных документах ссылаться на канонический раздел, локальные исключения описывать явно. Оба структурных JSON должны содержать одинаковое описание.
8. По решению пользователя от 2026-10-05 текущая реализация принята как базовая для этой синхронизации документов. Это не разрешение автоматически менять ДС вслед за любыми будущими несогласованными изменениями кода.

## 15) Политика использования субагентов

Цель:
- минимизировать засорение контекста основного агента;
- использовать основной агент как orchestrator и integrator.

Имена ролей:
- `Silvio` = `explorer`
- `Christopher` = `worker`

Правила:
- по умолчанию задачи исследования кода, поиска места изменений, проверки связей между файлами и сбора контекста делегировать `Silvio` (`explorer`)-субагенту;
- по умолчанию задачи написания, изменения и точечной доработки кода делегировать `Christopher` (`worker`)-субагенту;
- основной агент должен по возможности не выполнять детальную работу субагентов сам, если ее можно делегировать без потери качества, скорости и управляемости;
- основной агент отвечает за:
  - декомпозицию задачи;
  - выбор субагентов;
  - контроль границ ответственности;
  - сбор и проверку результатов;
  - финальную интеграцию;
  - финальный ответ пользователю.

Ограничения:
- не делегировать маленькие задачи, если это создает лишний overhead;
- не назначать разным субагентам одни и те же файлы или пересекающиеся зоны записи;
- если следующий шаг критически зависит от немедленного результата, основной агент может выполнить его сам;
- если задача требует только короткого локального действия быстрее, чем постановка и ожидание субагента, основной агент может выполнить ее сам;
- основной агент не должен дублировать уже делегированную работу без явной причины.

Правила постановки задач субагентам:
- при делегировании явно указывать:
  - цель;
  - зону ответственности;
  - можно ли менять код;
  - какие файлы или директории доступны;
  - что должно быть в результате;
- для `Christopher` (`worker`)-субагента всегда фиксировать границы записи по файлам или директориям;
- для `Silvio` (`explorer`)-субагента по умолчанию ставить read-only задачи, если нет отдельной причины разрешать изменения.

## 16) Прогрессивный блюр (обязательно)

- Перед добавлением или изменением progressive blur читать [каноническое правило в дизайн-системе](design-system-spec.md#progressive-blur). Подтверждённый пользователем эталон — `components/games/PixelPerfect.tsx` и `.progressiveBlurLayer` в `components/games/games-entry.module.css`. Повторно использовать этот механизм; не перепридумывать эффект при каждом запросе.
- Порядок деклараций обязателен: сначала `-webkit-backdrop-filter`, затем стандартный `backdrop-filter` с тем же значением. Не менять этот порядок при сортировке CSS. В установленном трансформере Lightning CSS обратный порядок удалял стандартное свойство из результата, и браузер вычислял `backdrop-filter: none`.
- Сохранять статичные перекрывающиеся blur-слои с индивидуальными масками и доступом к размываемым источникам. Анимировать исходные объекты, а не сами filter-слои; не добавлять между слоями и источниками обёртку, отсекающую backdrop. Точная структура и ограничения описаны в каноническом правиле.
- Параметры Pixel Perfect сохранять при несвязанных правках. В другом месте адаптировать направление и область эффекта под конкретный запрос, сохраняя механизм и правила дизайн-системы; параметры игры не объявлять универсальными токенами.
- Техническую диагностику progressive blur запускать только когда она допустима по разделу 10 и конкретная правка может повлиять на сборку CSS. Тогда сначала смотреть реально сгенерированный CSS; вычисленный `backdrop-filter`, поддержку браузером, маски и геометрию проверять только по отдельному явному запросу пользователя на такую диагностику. Для обычной UI-правки диагностику и проверки не запускать. Не пытаться исправить отсутствие CSS-свойства увеличением blur или перестановкой `z-index`.
- Визуальную оценку выполняет пользователь; не запускать её автоматически. Технические проверки не выполнять вопреки прямому запрету пользователя.
- Изменения самого правила синхронизировать с `design-system-spec.md`, `portfolio-structure.json` и `portoflio-structure.json`; изменения эталона игры также отражать в `docs/specs/games.md`.
